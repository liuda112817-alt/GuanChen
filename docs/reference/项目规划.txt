观尘 GuanChen v2
旗舰 AI Agent 项目完整建设规划
冻结版 v1.0
目标：从 0 系统重建一个可解释、可评测、可部署、可面试深挖的垂直领域 Agent Application
范围：八字分析 Agent｜解梦 Agent｜易经 / 六爻决策反思 Agent｜传统文化知识 Agent
执行纪律  本规划一经确认即作为 v2.0 建设基线。阶段内不因“顺手想到”而扩项；新增想法统一进入 v2.1 Backlog。只有阻塞当前阶段的正确性、安全性或不可运行问题，才允许触发变更。
1. 项目最终目标与建设原则
观尘 v2 的目标不是继续修补旧项目，也不是堆更多“玄学 Agent”。项目将从 0 重建，以四个职责差异明显的领域 Agent 为业务载体，系统练习 LLM 结构化输出、Tool Calling、RAG、Context / Memory、LangGraph、HITL、MCP、Evaluation、Observability 和生产部署。

1.2 建设总原则
现成库 / 官方 API 能稳定完成的确定性能力，优先直接调用；项目代码只负责适配、校验、业务契约和编排。
确定性计算不交给 LLM：历法、四柱、十神、卦象等由代码 / 库产生；LLM 负责理解、选择、解释和整合。
先单 Agent 闭环，再引入多 Agent；先普通 Python，再在真正需要持久状态、分支和 HITL 时使用 LangGraph。
只在风险高、容易回归或直接决定系统质量的地方安排测试。其余内容通过阶段验收脚本和人工样例验证。
不为了简历关键词添加架构。任何新组件必须回答：解决了什么已出现的问题？能否明显提升 Agent 岗位面试价值？
所有跨阶段新想法进入 Backlog，不插入当前阶段。v2.0 只执行本规划中的固定事项。

Stage 1｜工程骨架与 LLM 基础设施
阶段结果  建立最小但长期可演进的 Python 项目骨架，做到文本输出、结构化输出和错误处理稳定。
本阶段固定任务
使用 uv 初始化 Python 3.12 项目，建立 pyproject.toml、环境变量模板和 lockfile。

使用 pydantic-settings 建立单一配置入口：模型名、API Key、超时、重试、日志级别。
建立 LLMClient：普通文本调用、Pydantic 结构化输出、统一异常、有限重试；业务 Prompt 不负责输出协议。
使用 langchain-deepseek 的 ChatDeepSeek，不自行实现 DeepSeek HTTP 协议。
建立最小 Prompt 组织规范：system 与 user template 分离、模型输入序列化集中处理。
建立最小日志规范，禁止日志写入完整敏感用户内容。
写一个 scripts/smoke_llm.py，验证 text / structured 两种调用。

Stage 4｜RAG 基础设施 + 传统文化知识 Agent
阶段结果  建立项目唯一的知识检索底座，并让知识 Agent 与八字 Agent 共享，而不是每个 Agent 各做一套 RAG。
本阶段固定任务
冻结第一批语料：公版 / 可合法使用的《周易》《渊海子平》《三命通会》《滴天髓》《增删卜易》及自行整理的术语 / 注释；不批量抓取现代版权内容。
定义统一 KnowledgeDocument / KnowledgeChunk metadata：domain、source_title、section、source_type、chunk_id、text。
实现 ingestion：读取 → 清洗 → 按章节 / 段落语义切片 → metadata → embedding → PostgreSQL/pgvector。
Dense Retrieval：bge-small-zh-v1.5；Sparse Retrieval：bm25s + jieba；使用 RRF 合并候选。
实现 metadata filter，避免八字问题召回大量六爻文本。
实现 Reranker adapter（bge-reranker-base）；按固定性能门槛决定生产默认是否开启。
定义 RetrievalResult 和 Citation；回答必须能追溯 source_title / section / chunk_id。
实现 Knowledge Agent：检索 → 基于证据回答 → 证据不足明确说不足，不编造原典。
把 Retrieval Tool 接入 Bazi Agent，使八字解释从“模型常识”升级为“排盘事实 + 检索依据”。
建立 scripts/eval_retrieval.py 和固定黄金查询集。

Stage 5｜解梦 Agent：Context Engineering 与多轮任务
阶段结果  实现一个与八字完全不同的 Agent：核心不是计算 Tool，而是从多轮对话中维护梦境对象和现实上下文。
本阶段固定任务
定义 DreamElements：人物、场景、对象、行为、情绪、异常变化、用户主观感受。
定义 DreamRecord：原始描述、结构化要素、补充现实背景、当前解释状态。
使用结构化输出做梦境要素提取；提取只是理解，不直接得出结论。
建立“是否需要追问”的简单规则：只有缺少会显著影响解释的信息时才追问，避免问卷式体验。
构造检索查询：梦境象征 / 情绪 / 现实压力分别检索，结果仍走共享 Retrieval Service。
输出至少两个明确区分的视角：传统文化象征 + 非诊断性的心理 / 情境解释。
在当前 Python 会话内维护 DreamRecord，多轮补充时更新同一个对象，而不是重新解释一个新梦。
记录“当前进程内 session memory”的局限，持久化统一放到 Stage 8。

Stage 6｜易经 / 六爻决策反思 Agent + LangGraph HITL
阶段结果  第一次在“确实需要暂停、确认、恢复”的业务里引入 LangGraph。
本阶段固定任务
冻结 DecisionQuestion schema：用户原问题、澄清后的单一问题、现实约束、确认状态。
封装 ichingpy：生成 / 构造卦象、装卦 / 纳甲等确定性结构，统一映射成 HexagramResult。
起卦策略冻结：支持“系统随机三枚硬币法”和“用户手工输入六爻结果”；随机过程必须在回答中透明标注。
设计 LiuyaoState：question、clarification、confirmed、hexagram、citations、final_response。
使用 LangGraph：clarify → interrupt(confirm) → cast tool → retrieve → interpret → finalize。
只有用户明确确认问题后才允许起卦；取消 / 修改会回到澄清节点。
本阶段使用 InMemory checkpointer 理解 HITL；跨进程持久化留 Stage 8。
最终输出定位为“决策反思”，必须结合现实条件，不输出“必须辞职 / 必须投资”等绝对指令。

Stage 7｜统一 Router 与多 Agent 编排
阶段结果  把四个已经独立可用的 Agent 接入一个统一入口；只在明确跨领域问题时进行有限并发。
本阶段固定任务
定义 IntentType：BAZI、DREAM、LIUYAO、KNOWLEDGE、CHITCHAT、OUT_OF_SCOPE。
定义 RoutingResult：primary_intent、secondary_intents（最多 1 个）、confidence、required_data、reason。
建立两层路由：高精度规则命中明显请求；其余交给结构化 LLM Router。
单领域请求只调一个 Agent；知识问答不先跑八字资料检查。
只支持显式双领域场景，例如“结合八字和昨晚的梦看一下”；最多并发两个 Agent。
为双领域结果建立 Synthesizer，只整合两方已有结论 / 证据，不制造新的第三套推演。
统一顶层 ConversationGraph：load context → route → requirement check → agent(s) → synthesize / direct → response。
删除全局预先 RAG：每个 Agent 只在需要时调用 Retrieval Tool。
建立路由黄金数据集。

Stage 8｜Memory 与持久化
阶段结果  把此前的进程内状态升级为可恢复的真实产品状态，同时严格区分 thread state 与长期用户资料。
本阶段固定任务
设计 PostgreSQL 表：user_profile、birth_profile、conversation、message、dream_record、decision_record。
使用 SQLAlchemy async repository；只为真实持久化需求创建 repository，不做抽象接口层套娃。
将 LangGraph checkpointer 升级到 PostgreSQL 持久实现，使 HITL thread 可跨进程恢复。
长期 Memory 只保存“用户明确提供 / 确认”的结构化资料；不自动从每句话抽取人格、价值观等隐式事实。
实现 Memory Selector：八字只读取 BirthProfile + 相关近期对话；解梦读取当前 DreamRecord；六爻读取当前 DecisionRecord。
建立 Memory namespace / domain 隔离，防止梦境上下文污染八字分析。
实现用户更正：后写的明确更正覆盖当前有效事实，并保留 updated_at；v2.0 不做完整版本树。
PostgreSQL 已由 Stage 4 使用 pgvector，本阶段复用同一数据库。

Stage 11｜Safety、FastAPI、SSE 与现有前端整合

10. 旧版项目只作为需求原型与反例库
旧版源码不作为新项目代码基线。它保留的价值是：帮助我们识别哪些能力确实值得做，以及哪些“看起来工程化”的模块如果没有真实闭环会伤害体验。
旧版观察
v2 对应原则
Graph 中真实 Router 与依赖注入没有完全闭环
Stage 7 才做统一 Graph，并要求真实端到端验收。
所有请求可能先依赖 BirthProfile
Stage 7 / 11 改成 Route 后按 Agent 需求补资料。
RAG ingestion / query 的 collection、metadata、embedding 契约可能不一致
Stage 4 先冻结 KnowledgeChunk schema，再写 ingestion 与 retrieval。
注释声称真太阳时，但经纬度没有真正参与算法
v2.0 直接声明不做真太阳时，不制造“看起来支持”的能力。
大量重试、熔断、Risk Matrix 先于真实业务稳定
可靠性只在已经出现真实故障 / 上线需要时加入。
